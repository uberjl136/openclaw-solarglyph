## 作品简介

工业厂区屋顶光伏在方案阶段要回答"一年发多少电、余热还能回收多少"，目前依赖人工套用 Excel 公式，慢且无法复现。我们以开源智能体框架 OpenClaw 为底座，新增垂直场景 Skill「solar-glyph-simulation」，把光伏发电与工业余热回收的工程算法做成可调用的 HTTP 仿真服务，实现"一句自然语言指令 → 下发任务 → 轮询状态 → 取回结果"的全自动闭环。相对上游，我们未改动任何底层源码，而是新增了 Skill 定义、自研仿真服务与逐条算法溯源文档（20 条公式对照，并明确区分复现与自研边界），其中工业余热回收模块为团队原创。实测：5 MWp 厂区年发电 499.5 万 kWh、余热年回收 315.2 万 kWh、年减排 CO₂ 1776 吨；Skill 被 OpenClaw 识别为 ready，确定性入口与模型驱动入口均已跑通并通过 7 项自动校验。

## 一、作品概述

### 1. 背景与问题

**目标用户**：分布式光伏项目的方案工程师、能源管理岗，以及需要快速评估屋顶光伏与余热回收潜力的工业厂区技术人员。

**使用场景**：厂区屋顶光伏项目在可行性研究与方案比选阶段，需要反复回答同一类问题——
按给定装机容量、朝向倾角与当地辐照条件，项目首年/年均可发电多少？如果用余热回收补充供热或发电，还能多出多少可用能量、减排多少？

**现有做法与痛点**：

1. **人工核算慢且不可复现**。目前通常在 Excel 中套用辐照—发电量经验公式，每次改参数都要重算，中间假设散落在个人表格里，评审无法追溯。
2. **通用 AI 智能体缺行业算法**。我们实际枚举了上游 OpenClaw 的 57 个内置能力，覆盖笔记、邮件、GitHub、天气、智能家居、调试等通用任务，**没有任何一项涉及光伏、辐照、余热、储热或电力工程计算**。直接向它提问，只能得到定性描述，拿不到可核对的工程数字。
3. **现成工具是黑盒**。商业仿真软件不开放算法口径，无法核对中间量，也难以嵌入自动化流程。

**具体问题界定**：让通用智能体具备"光伏 + 余热"的垂直仿真能力，并把一次评估从"人工数天"压缩到"一句指令、数秒出结果、结果可复现"。

### 2. 目标、参赛方向与作品形态

**目标**：在开源智能体框架 OpenClaw 之上，形成可运行、可演示、可核验的新能源仿真能力闭环。

**参赛方向**：本作品申报第三方向「**开源项目改进与生态贡献**」。理由：作品选择一个具有合法开源许可证的上游项目（OpenClaw，MIT）开展二次开发与功能增强，交付物为新增的 Skill、配套服务与文档，并在技术报告中明确说明上游项目、许可证、自主完成内容以及相较原项目的实质改进。

**作品形态**：智能体 Skill（插件形态）+ 配套的自研仿真服务（HTTP 服务）。

**所做工作与原项目的关系**：不修改上游源码，以"新增"而非"改写"的方式扩展——上游原版能力保持不变，可随时用官方发布包比对。

### 3. 核心亮点

1. **把前端工程算法服务化**。目标工程平台 `solarglyph.newenergycoder.club/simulation` 是纯前端应用，服务端只有登录与地理编码接口，**不提供仿真 API**。我们把其中的工程算法固化为带任务队列的 HTTP 仿真服务，从而具备可被程序调用的能力。
2. **新增垂直场景 Skill 并打通全自动闭环**。Skill 声明触发词与四步执行流程，Skill 与仿真服务之间通过真实 HTTP 交互（提交返回 202、轮询状态、取回结果），并保留确定性调度入口（不依赖模型即可复现）。
3. **算法口径逐条可溯源**。20 条公式逐条对照到原工程产物的具体位置，并明确标注哪些是复现、哪些是团队自研扩展。
4. **自研工业余热回收模块**。原工程内容不包含余热回收，本模块支持空压机余热、燃气锅炉烟气、循环冷却水、逆变器散热四类典型工业热源，并给出 ORC 发电、直接供热与 CO₂ 减排量。
5. **可验证的实测效果**。所有结论均有实测输出与服务端任务记录支撑，验证方法与结果见第五章。

## 三、AI 技术与开源及第三方资源选择

### 1. AI 技术在作品中的作用

人工智能在本作品中承担的是**理解与自动化执行**，具体环节：

1. **意图理解**：把"启动光伏余热仿真"这类中文自然语言映射为具体任务。
2. **能力选择**：从智能体可用工具中选出 `exec`，并决定调用 Skill 自带脚本。
3. **流程编排**：按 SKILL.md 规定的步骤依次完成健康检查、下发任务、读取结果。
4. **结果汇总**：把服务返回的工程指标转述成用户可读的结论。

**为什么需要 AI**：仿真本身是确定性计算，但"把用户的口语需求翻译成正确的调用参数与流程"是开放式的，传统规则引擎难以覆盖表达差异，这正适合由智能体完成。AI 负责"决定做什么"，自研仿真服务负责"算得准"，两者职责分离。

**如何验证 AI 输出**：不依赖模型自述。所有结论以**仿真服务的任务记录**与**脚本返回的数值**为准，例如通过 `GET /v1/simulations` 查询任务历史，确认模型确实提交并完成了仿真。同时用确定性入口（绕过模型）复现同一组数值，形成交叉验证。

### 2. 开源及第三方资源选择

详见附录《开源及第三方资源使用清单》。选型要点：

| 资源 | 选型依据 |
| --- | --- |
| OpenClaw（MIT） | 成熟的智能体底座，具备 Skill 体系、工具调用与控制面，且**支持在不改源码的前提下新增能力** |
| Node.js | 仿真服务与 Skill 脚本的运行环境；上游要求 Node 24 系列 |
| pnpm 12.3.4 | 上游指定的包管理器版本 |
| Ollama + Qwen 系列模型 | 本地模型方案，用于在无云端凭据环境下验证模型驱动路径 |

### 3. 自主开发与权利边界

**第三方开源部分（原样使用，未修改）**：OpenClaw 全部上游源码，以官方发布包快照形式引入，字节级一致。

**团队自主完成部分**：

| 成果 | 说明 |
| --- | --- |
| Skill 定义 `SKILL.md` | 触发条件、四步执行流程、参数表、HTTP 契约、安全边界 |
| 桥接 CLI `run-simulation.cjs` | HTTP 客户端、进度轮询、文本/JSON/Markdown 输出、报告落盘 |
| 触发映射 `trigger.cjs` | 中文触发词 → 场景预设的确定性映射 |
| 仿真引擎 `engine.js` | 太阳位置、倾斜面几何、辐照—发电量、储热、电气校核、**余热回收（原创）** |
| 场景预设 `presets.js` | 四套场景 + 工业热源参数库 |
| HTTP 服务 `server.js` | 异步任务队列、阶段化进度、输入校验、错误语义 |
| 工具链与文档 | 安装/同步/校验脚本、算法溯源、实测证据、部署说明 |

**AI 工具完成部分**：见第四·3 节披露。

### 4. 融合方式（为何不是简单调用接口）

本作品不是"调用一个通用模型接口"，而是三层耦合：

1. **能力层**：上游框架提供智能体循环、工具调用与 Skill 加载机制——这是"能干活"的前提；若换成没有 Skill 体系的项目，本作品无法以同样方式落地。
2. **垂直层**：我们新增的 Skill 定义了"收到什么话该做什么事"的行业逻辑，并自带可执行脚本，使行业能力可以被框架原生调度。
3. **算法层**：自研仿真服务承载行业工程算法，是"算得准"的唯一来源；框架本身不具备该能力。

相较"通用 AI 应用"的实质改进：**通用模型能说但算不了行业数**，本作品把口径明确、可溯源、可复现的工程计算接进了智能体，并以服务端任务记录作为可核验证据。

## 四、设计与实现过程

### 1. 核心功能与流程

| 功能 | 输入 | 输出 |
| --- | --- | --- |
| 服务健康检查 | 无 | 服务状态、模型元信息、端点清单 |
| 下发仿真任务 | JSON 参数或预设名 | `202` + 任务号 + 轮询链接 |
| 轮询任务状态 | 任务号 | 状态、阶段、进度百分比 |
| 取回仿真结果 | 任务号 | 关键指标、热源明细、代表日逐时曲线 |
| 产出报告 | 结果 + 输出路径 | Markdown 报告文件 |
| 参数校验 | JSON 参数 | 合法/非法判定与逐字段错误说明 |

**典型操作流程**（Skill 规定的四步）：

1. 健康检查：`run-simulation.cjs health`，若服务未启动则先拉起 `server.js`；
2. 下发任务：`POST /v1/simulations`；
3. 轮询状态：`GET /v1/simulations/{id}`，直到 `succeeded`；
4. 取回结果并回报指标，必要时用 `--report` 落盘 Markdown。

### 2. 关键实现

**（1）Skill 的触发与调度设计**

`SKILL.md` 的 frontmatter 声明 `name`、`description`（内嵌触发词）与 `command-dispatch: tool`。
前者让模型在自然语言场景下发现并采用本 Skill；后者提供**绕过模型的确定性入口**，
斜杠命令直接触发脚本，用于离线演示与可复现验证。

**（2）异步任务语义**

仿真服务实现真实的任务生命周期：
`queued → loading-site-inputs → transposing-irradiance → solving-pv-and-waste-heat → aggregating-results → succeeded`。
提交返回 `202` 与 `Location`；未完成时取结果返回 `409 result_not_ready`；未知任务返回 `404`；非法参数返回 `422`。

**（3）工程算法固化**

从目标工程平台的前端产物中定位并复现以下算法，并逐条记录来源：

- 太阳几何：赤纬角、时角、太阳高度角、倾斜面入射角；
- 月度倾斜面几何指数与月度辐照分配；
- 发电量：单位发电量路径（原站点口径）与辐照—性能比路径（含组件温度修正）；
- 储热：储热量、圆柱几何近似、热损 `U≈λ/t`、充放热时长；
- 电气：逆变器交流电流、导体电阻、线路电压降；
- 光伏蓄冷匹配（复现原站点结论）。

**（4）余热回收模块（团队原创）**

单路热源：`Q_avail = ṁ·c_p·ΔT`；`Q_recovered = min(Q_avail, Q_pinch) × η_recovery × availability`；
年回收热量按可用率折算。多路汇总后给出 ORC 发电量（`Q_year × η_ORC`）、
可用供热量（`Q_year × η_heat`）与减排量（乘电网排放因子）。

**（5）确定性保障**：同输入必得逐字节相同输出，并以自动校验脚本强制检查。

**（6）可离线运行的精简配置**：把智能体可见工具面收窄到流程必需的 `read` 与 `exec`
（系统提示中的工具 schema 由约 66 KB 降至约 2.6 KB），并关闭工作区引导注入，
使本地 8B 模型也能稳定完成工具编排。

### 3. 团队分工与过程记录

| 环节 | 承担方 | 说明 |
| --- | --- | --- |
| 需求界定与场景选择 | 团队 | 确定聚焦"光伏 + 余热"垂直场景 |
| 算法提取与口径确认 | 团队 | 定位前端产物中的工程算法，逐条核对 |
| Skill 与仿真服务设计实现 | 团队主导，AI 辅助 | 由 AI 生成代码初稿，团队指定接口与流程并逐轮修改 |
| 验证与测试 | 团队 | 设计校验项、执行实测、核对服务端任务记录 |
| 文档撰写 | 团队主导，AI 辅助 | 报告与文档由 AI 起草，团队核对数据与表述 |

**生成式 AI / 智能体使用披露**：开发过程中使用了 AI 编程助手生成代码与文档初稿。团队的审核与核查工作包括：

- **功能审核**：逐项运行校验脚本，确认 Skill 包完整性、自包含性、确定性；
- **数值核查**：用确定性入口复现仿真数值，与预期量级和公开工程经验比对；
- **来源核查**：算法逐条回溯到原工程产物的具体位置并记录，避免无出处引用；
- **权利核查**：确认上游许可证与再分发条件，保留 LICENSE 与署名；
- **修改验证**：AI 生成内容不直接采信，须经人工修改并在真实运行环境中验证后才纳入作品。
- **服务条款遵守**：仅使用本地模型与开源软件，未调用受限商业接口。

## 八、总结与展望

### 1. 项目总结

本作品在开源智能体框架 OpenClaw 之上，新增了垂直场景 Skill「solar-glyph-simulation」与配套的自研
光伏—余热仿真服务，打通了"自然语言指令 → 下发任务 → 轮询状态 → 取回结果"的全自动闭环，
并交付了逐条可溯源的算法文档与实测证据。

**主要价值**：把原本依赖人工、口径不透明、难以复现的方案评估，变成一句指令即可完成、
结果确定性可复现、且能嵌入自动化流程的能力。
