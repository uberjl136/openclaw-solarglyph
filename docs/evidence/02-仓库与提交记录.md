## 四、上游零修改证明（本作品的核心主张之一）

作品说明书里写的是「**未改 OpenClaw 底层源码**」。这条主张可以用两条命令验证。

### 证据 1：只有一个提交触及上游目录，且它标注了 unmodified

```bash
git log --oneline -- upstream/
# 38ac45bc vendor(upstream): OpenClaw source snapshot at ad1c934 (unmodified)
```

**总共 1 个提交**，就是快照导入本身；提交信息里写明 `unmodified`。
导入之后**没有任何提交修改过 `upstream/` 下的任何文件**。

### 证据 2：我们的改动全部是新增目录，不落在上游路径

按顶层目录统计各提交的文件变更次数：

| 顶层路径 | 文件变更次数 | 性质 |
| --- | --- | --- |
| `upstream/` | 43,458 | **仅快照导入这一次**，之后零改动 |
| `docs/` | 24 | 文档 |
| `scripts/` | 21 | 工具脚本 |
| `skills/` | 7 | **自研技能** |
| `README.md` | 7 | 说明 |
| `package.json` | 4 | 项目配置 |
| `solarglyph-core/` | 3 | **自研仿真服务** |
| 其他（LICENSE、.gitignore 等） | 6 | 项目骨架 |

### 证据 3：技能是「装进工作区」，不是「补丁进源码」

实测运行 `openclaw skills list` 时，两个来源标记可以区分：

```
| ✓ ready | ☀️ solar-glyph-simulation | ... | openclaw-workspace |   ← 我们新增的
|         | 1password                | ... | openclaw-bundled   |   ← 上游自带的
```

`openclaw-workspace` 表示该技能来自工作区目录（即安装进去的扩展），
`openclaw-bundled` 表示框架自带。**这套作品加的是前者。**

## 五、一次误删记录（如实保留）

2026-10-25 前后，仓库维护者清理重复目录时删掉了顶层的 `solarglyph-core/`。
看似与技能内的副本重复，实际该目录是**载荷目录**：

- `package.json` 的 `npm start` 指向它
- `docs/deployment.md` 教读者运行它
- `scripts/verify-skill.cjs` 用它作为「副本是否被手改」的参照

删除后 `npm start` 与 `npm run verify-skill` 同时报 `ENOENT`，按 README 操作的读者会失败。

**处理**：从技能副本逐字节恢复（恢复前后均比对 SHA-256），并新增
`solarglyph-core/README.md` 说明「源 / 副本」关系与不可删除的原因，防止再次发生。
对应提交 `2f8e6e90`。

> 保留这段记录的原因：证伪比自述更有说服力。这条能同时说明我们**真的在本地跑过全部命令**
> （否则发现不了这个断点），以及**发现问题后如何修复**。
